# A hybrid of the code graph and PageIndex RAG

**Status: built and measured on four repositories.** `modules/index-tree` derives the tree,
`TreeNavigator` descends it, `NavigationSession` lets an assistant drive that descent, and
`RetrievalHarness` measures the result. `HYBRID` is never worse than flat retrieval and better on
two of four corpora; at scale the descent is also two to three times *cheaper* than flat ranking,
because it reads 18 cards where ranking scores 45,000 nodes. Running the real corpora found three
defects the fixture could not — see [the retrieval baseline](benchmarks/retrieval-2026-09-09.md).

## The idea in one sentence

PageIndex-style RAG replaces "embed chunks, rank by vector similarity" with "build a table of
contents, then let a reasoner walk down it". This does that over the code graph instead of over
document text: derive a navigable tree from what the graph already proves, descend it to choose
*where to look*, then use the graph's edges to decide *what to return*.

Retrieval was the weakest layer in this product. That is the layer this changes. The verification
gate, the provenance rules, and the deterministic model underneath are untouched.

## What PageIndex RAG actually does

Worth stating precisely, because the value of the hybrid depends on which parts transfer.

1. **Index time.** A long document is turned into a hierarchical tree that mirrors its own structure
   — a table of contents. Each tree node carries an id, a title, a short summary, its children, and
   a pointer to the physical region it covers (in PageIndex's case, a page range).
2. **Query time.** The reasoner is shown one node's card — its summary and the ids of its children —
   and picks which children to descend into. It repeats down the levels, keeping a small set of
   candidate branches, until it reaches leaves.
3. **Read.** Only the selected leaves are fetched and read.

Three consequences follow, and all three matter here:

- **No embeddings and no vector store.** Retrieval is a sequence of small reasoning steps over
  structure, not a nearest-neighbour lookup.
- **No fixed-size chunking.** The unit of retrieval is a section the document itself defines, not an
  arbitrary 800-token window.
- **The descent is inspectable.** You can read the path the reasoner took and see where it went
  wrong, which a cosine score cannot give you.

The relevance-by-similarity assumption is what PageIndex drops. "Semantically nearest" and "actually
relevant" diverge badly in code, where `PaymentService`, `PaymentServiceTest`,
`LegacyPaymentService` and a `payment` field on an unrelated DTO all look alike to an embedding and
mean entirely different things to an engineer.

## Why this repository was an unusually good host for it

Three facts about the code as it stood, each of which the hybrid depends on.

**The hierarchy already exists, unmaterialized.** `Modules.detect` derives subsystems from build
layout or package prefix. `Capabilities.detect` groups the operational surface by route root and
topic root. `Workflows` walks every entry point to the tables and topics it touches. Packages,
types, and members are in the graph from the analyzer. That is a five-level table of contents
already, expressed only as `CONTAINS` and `PARTICIPATES_IN` edges — never assembled into something
navigable.

**Retrieval was flat and landed on exactly one anchor.** `Bm25Index.over(graph)` indexes every
non-external node as an independent document with no notion of containment, and `QueryPlanner.plan`
then narrowed to `Optional<GraphNode> subject`. Questions with inherently plural answers — "which
endpoints touch the owners table", "what does the billing module depend on" — could not be answered
well by construction, and `compress()` encoded the same assumption by sorting evidence on whether an
edge touched that one subject. Anchoring is now a set, and both of those follow it.

**The roadmap already named the missing measurement.** Milestone 4 records that ranking quality
"is the next missing metric, and the one that matters for large repos". A tree navigator is
precisely a ranking mechanism, so it could not honestly be evaluated until that metric existed —
which is why `RetrievalHarness` was built first.

There is also a fourth alignment worth noting. The roadmap says a vector RAG baseline is still
blocked because it "needs an embedding model that runs locally without credentials". PageIndex-style
retrieval needs no embedding model at all. In its deterministic form it needs no model at all.

## Where the analogy transfers, and where it breaks

| PageIndex over documents | This, over the graph |
| --- | --- |
| Tree is generated by an LLM reading the document | Tree is **derived deterministically** from graph structure |
| Node covers a page range | Node covers a **set of graph node ids**, each with file:line provenance |
| Node summary is model-written prose | Summary is deterministic facts, plus an **optional pinned claim** capped at 0.80 |
| Leaves are read as raw text | Leaves are expanded into a `ContextPacket` and **traversed** |
| Document has no cross-references | The graph has edges, so retrieval does not stop at the leaf |

The last two rows are where the hybrid beats both parents. A tree tells you *where* the relevant
region is; it cannot tell you that a change there breaks a controller three hops away. The graph
can. Descent locates, traversal reaches.

The first row is where it beats PageIndex on integrity. PageIndex must trust a model to build the
tree correctly, because a document's structure is only recoverable by reading it. A Java repository
states its structure — build layout, packages, declarations, routes — so the tree can be derived
under the same evidence rules as every other layer here, and re-derived byte-identically.

## The design

```text
CodeGraph (deterministic, schema 0.3)
   │
   ├─ derive ──▶ IndexTree                    index:repo
   │             pinned artifact                 └─ index:module:…
   │             + graph fingerprint                 └─ index:capability:… | index:package:…
   │                                                     └─ index:type:…
   │                                                         └─ leaves → { METHOD, ENDPOINT, TABLE, TOPIC }
   │                                             every node lists the graph ids it stands for
   │
question ──▶ QueryPlanner.classify              unchanged: keyword, fast, inspectable
         ──▶ TreeNavigator.descend(tree, …)
         │      ├── Chooser.DETERMINISTIC       card BM25 × exact-name match × query-kind affinity
         │      └── NavigationSession           offline file protocol; chooses only presented ids
         ──▶ anchor SET  (not one subject)
         ──▶ GraphQueries.context per anchor → merge → compress to budget
         ──▶ VerifiedAnswer.verify              unchanged gate, unchanged invariants
```

### The node card

This is the PageIndex summary page, translated. It is what a navigator — deterministic or model —
actually sees:

```text
index:capability:owners          kind=BUSINESS_CAPABILITY   graphIds=[capability:owners]
  entryPoints 6   entities 2   types 4   unresolvedEdges 3
  exemplars: OwnerController, OwnerRepository, table:owners, GET:/owners/{ownerId}
  children:  index:endpoint:GET:/owners/{ownerId}
             index:endpoint:POST:/owners/new
             index:type:org.springframework.samples.petclinic.owner.OwnerController
             …
  summary (claim ≤0.80): "Owner registration and lookup"
```

Every line above the summary is derived. The summary line is the one place a model's opinion
appears, and it arrives through machinery that already exists: `EnrichmentClaims.ClaimKind.NAME` and
`SUMMARY`, capped at `MAX_CLAIM_CONFIDENCE`, pinned to a committed claims file, verified before
application. `Capabilities` anticipates exactly this in its own javadoc — naming a capability
"Owner registration" rather than "owners" is the ambiguous, high-value judgement the enrichment
budget exists for.

The corollary is a scheduling insight: **enrich branch nodes, not leaf methods**. One good summary
on a high-fan-out branch steers every descent that passes through it. A summary on a leaf method is
read once.

`BranchEnrichment` ranks on exactly that, by reach (how many symbols sit below), choices (how many
children the card presents — a branch with one child disambiguates nothing), and opacity (how little
the name already says), with test code discounted because no question routes through it. The
difference from ranking symbols is stark on jackson-databind: the same 2,000-token budget buys
summaries of `type`, `util`, `misc` and `deser.impl` instead of `ObjectMapper#readValue`, three
`Map#get` overrides, and a test utility called `a2q`.

It produces candidates for the machinery that already exists, so a summary arrives as a
confidence-capped `claim.summary` on the graph node the branch covers, and `IndexTreeBuilder` reads
it back onto the card.

**Whether real summaries improve descent was measured twice, and the answer is no.**

The first run, on Petclinic, appeared to show a lift: anchor recall 0.737 → 0.842 on questions that
do not name their subject, with "which table stores the clinic's clients" answerable only because a
summary called `Owner` "a client of the clinic", a word absent from the source. But one author wrote
both the summaries and the questions.

The second run separated them. Questions for jackson-databind and junit5 were written and committed
first; the summaries were then extracted mechanically from each project's own `package-info.java`
javadoc, prose written by maintainers who have never seen the questions. 26 summaries, 0 rejected,
**not one metric moved and not one question recovered**.

The reason is precise. The summaries are not empty — 91% and 70% of their words are new to the
branch — and they reach the cards. They simply never say what the asker said: "JUnit Jupiter API for
writing tests" contains none of *annotation*, *runs*, *before*. So the claim this design makes for
summaries survives only in a much narrower form: a summary helps exactly when it happens to carry
the words the question will use. One author writing both nearly guarantees that; independent
authorship makes it coincidental, and across two real repositories it did not happen once.

### Navigation, and why a model here is safe

Beam search over cards, with a node budget. Two interchangeable navigators behind one interface:

- **`Chooser.DETERMINISTIC`** takes the highest scoring children, where the score is BM25 over the
  card's text plus a bonus for naming the question's subject exactly, multiplied by a query-kind
  affinity — `ENDPOINT` favours capability and endpoint branches, `PERSISTENCE` favours table
  branches, `STRUCTURE` stops at module level rather than descending to methods. Needs no model, no
  credentials, no network. This is the default.
- **`NavigationSession`** hands the same card to an assistant through a file exchange, in the shape
  `docs/enrichment-with-a-chat-assistant.md` already establishes: `repo-intel navigate` writes the
  cards at the frontier, the assistant answers with chosen ids, the next invocation advances one
  level. **An id that was not on the cards is rejected, not followed.** The product still never
  calls a model.

The safety property is structural rather than procedural: a navigation choice is not a claim. The
model selects from a fixed set of ids it was shown; it never asserts a fact, never names a symbol,
never proposes an edge. So it needs no confidence tier, no dispute path, and no new verification
rule. A bad descent costs recall, which the benchmark measures. It cannot corrupt the model.

Contrast that with what a summary is: an assertion about what code means, which goes through the
existing claims gate precisely because it *can* be wrong in a way that matters.

### Multi-anchor output

Descent naturally yields a set of leaves, not one. That is the point, and it was the change with the
largest blast radius in the existing code:

- `Answerable` gained `anchors` and `contexts`; `subject` and `context` stayed as the primary, so
  the single-anchor path is byte-for-byte the behaviour it was.
- `compress(packet, anchorIds, budget)` ranks every anchor's edges at the front of the sort together,
  rather than letting the first anchor's edges crowd the rest out.
- `claimsFrom(packet, anchorIds)` anchors each claim on the anchor its own cited edge touches. The
  existing refusal to attribute a one-hop edge to the wrong subject was extended, not loosened.

## What was built

| Phase | State | Where |
| --- | --- | --- |
| 0 — measure what is being replaced | done | `RetrievalHarness`, `evaluate --retrieval-only` |
| 1 — derive the tree | done | `modules/index-tree`, `repo-intel index` |
| 2 — deterministic navigator | done | `TreeNavigator`, `ask --retrieval BM25\|TREE\|HYBRID` |
| 3 — multi-anchor packets | done | `QueryPlanner.merge`, `compress(packet, anchors, budget)`, `ask --anchors` |
| 4 — assistant navigator | done | `NavigationSession`, `repo-intel navigate`, `ask --from-session` |
| 5 — branch summaries | done | `BranchEnrichment`, `enrich-targets --branches`, `enrichment-plan --branches` |

Two deviations from the plan above, both because the plan was wrong:

**precision@k is not reported.** Each grounded question declares one relevant symbol, so precision@k
cannot exceed 1/k and would measure that cap rather than the ranking. The harness reports recall@k,
MRR, and anchor recall, and says in its own output why the fourth metric is missing.

**The tree is derived by default, not loaded from a file.** Derivation costs about 80 ms on a 2,400
node graph, so requiring a pinned file for every query would have been ceremony. `--index` takes a
pinned tree where one is wanted — for an assistant descent, or to share one — and it is fingerprint
checked against the graph before use.

## What the measurement actually showed

Across the fixture, spring-petclinic, jackson-databind and junit5:

- **HYBRID is never worse than flat retrieval**, and better on two corpora — the fixture (MRR 0.950
  against 0.833) and junit5 (0.938 against 0.875). On the other two flat retrieval already scores
  1.000.
- **TREE alone is not a safe default.** It loses one question on junit5 to exactly the wrong-branch
  commitment this design predicted, which is why `--retrieval` still defaults to `BM25`.
- **At scale the descent is cheaper than the ranking**: 101 ms against 273 ms on jackson-databind,
  56 ms against 153 ms on junit5. Cards read per question barely moves between a 72-node graph
  (11.8) and a 45,595-node one (18.2), because depth grows logarithmically while flat ranking grows
  linearly. That crossover is the property the whole approach rests on, and it holds.

Running the real corpora was also where the design was found to be wrong three times over: a branch
card could not be searched for what it contained (jackson-databind scored **0.400** against flat
retrieval's 1.000), term frequency could not express "is it in here", and a question word was being
read as the subject (Petclinic fell from 1.000 to **0.800**). The benchmark records each one.

The capability this makes possible is now measured too, by anchor coverage — how much of a plural
answer the anchor set itself reaches. On Petclinic, flat retrieval scores **0.000** and tree descent
**0.561**, the widest separation between the modes anywhere in the benchmark: asked which routes a
controller exposes, flat ranking returns ten spellings of the controller's own name and no endpoint
at all. Coverage rises with the anchor budget and plateaus at beam 8.

What remains unmeasured is a question no single anchor can answer. Every plural question in the
corpus is still traversal-reachable from one subject, because the architecture layer's capability and
module nodes give a plural answer somewhere to hang from.

## The configuration to expect to win

Not tree-instead-of-BM25. **The union of both.**

Tree descent produces structurally coherent anchors and fails by committing to a wrong branch early.
Flat BM25 produces incoherent anchors and never has that failure mode, because it never made a
choice. Taking top-*n* from each, deduplicating, and splitting the budget covers the other's
weakness. That is what `HYBRID` means.

**On 53 questions this was measured and held. On 200 it does not.** `HYBRID` wins outright only on
spring-petclinic, splits on the fixture, and is indistinguishable from flat retrieval on both large
repositories. The union argument above is still sound about *failure modes*; it was simply never the
thing that decided these numbers. See [the 200-question corpus](benchmarks/corpus-200-2026-09-16.md).

Early branch commitment is worse on code than on prose, because names repeat across modules in a way
section titles in a document do not. `OwnerController` and `OwnerRestController` in different source
roots are a realistic way to lose a descent at level one.

## Invariants this must not break

| Invariant | How the design holds it |
| --- | --- |
| Same source, same output, any machine | Tree derived by sorted traversal; no `Set.of`/`Map.of` on any ordering path — the hazard `docs/architecture.md` explicitly flags |
| No relation without evidence | Tree nodes point at graph ids; they assert nothing the graph does not already carry |
| A model may describe, not extend | Navigation selects presented ids; summaries go through the existing claims gate at ≤0.80 |
| Deterministic path needs no LLM | `Chooser.DETERMINISTIC` is the default and is model-free end to end |
| Local-first, no network | Assistant navigation is a file exchange, identical in shape to `enrich-targets` / `enrich-apply` |
| Ids are stable and non-colliding | Tree ids are prefixed `index:`, asserted in a test and in CI, and live outside graph schema 0.3 |

## Risks, and what became of them

**Degenerate repository shapes — handled.** jackson-databind and junit5 prove no capabilities at
all, so both get the structural axis alone and the `index` command says so in its output. Both were
run: jackson-databind builds 26,530 entries at depth 5 with 1,015 grouped sibling sets, junit5
18,841 at depth 7 with 814. The extreme case — one module, one flat package, no framework, so both
axes collapse and only type names remain to steer by — is covered by tests: the package level is
collapsed away rather than left as a chain of one, every type stays reachable through its groups,
and a descent still routes to the right type among thirty look-alikes.

**Fan-out — handled.** Oversized sibling sets are chunked into alphabetical groups, recursively, so
no card presents more than `--max-fanout` choices and nothing is dropped to achieve it. This
repository triggers it 18 times; the fixture never does. A test asserts every one of 40 types stays
reachable through the groups.

**Index cost — measured.** About 80 ms on a 2,405 node graph, once per graph rather than per query.

**Staleness — handled.** The tree carries a SHA-256 of the graph's canonical export, and a pinned
tree is refused against a different graph with a message naming the fix.

**Latency in assistant mode — inherent.** A descent costs one round trip per level, against zero for
the deterministic chooser. The fixture descends in two steps.

**A defect this work exposed.** Deriving a tree from a `.json` graph produced three entries instead
of a thousand. The cause was in the graph reader, not the tree: it located the edge array by
searching the document text for `"edges"`, and this repository declares `CodeGraph#edges()`, whose
node is written as `"name":"edges"` far earlier. Every graph file from such a repository read back
with no edges, silently — `impact` answered "nothing is affected" rather than failing. Fixed, with a
regression test and a CI gate that checks a graph file answers the same as the repository it came
from.

## What this deliberately does not do

- It does not replace BM25. Flat retrieval stays as a baseline, as an escape hatch, and as half of
  the hybrid.
- It does not put the tree inside graph schema 0.3. Separate artifact first; fold it in only if it
  earns the churn.
- It does not make the assistant navigator the default, or reachable without an explicit
  `navigate` session. It is an option where a model is available, never a dependency.
- It does not let a model author tree structure. A model may name a branch. It may not invent one.

## Revision: what 200 questions changed, and the architecture that follows

Everything above describes a tree whose cards are built from **identifiers**. Four independent
measurements have now said that is the binding constraint, not the tree:

| Intervention | Result |
| --- | --- |
| Hand-written branch summaries | +0.105 anchor recall on Petclinic — contaminated, same author wrote summaries and questions |
| The same experiment run blind | 26 summaries, **zero** metrics moved, zero questions recovered |
| Build classpaths (77% → 99% resolution) | **Zero** retrieval metrics moved |
| The tree itself, at 200 questions | Indistinguishable from flat retrieval on both large repositories |

And one measurement that explains all four. Split the 200 questions by whether the question says its
subject's name:

| | found |
| --- | ---: |
| names its subject | 38/39 = **0.974** |
| describes it instead | 29/161 = **0.180** |

Each intervention enriched the *structure around* identifiers while leaving identifiers the only
vocabulary retrieval can match. The gap is lexical, and nothing tried so far touches it.

### Two models, not one

The fix is contextual enrichment — embedding a description of what a node *does* rather than what it
is called. That requires two different models, and conflating them is a distribution error this
library cannot afford:

| | writes the context | encodes it |
| --- | --- | --- |
| Kind | generative (1–7B+) | embedding encoder (22–33M) |
| Size | GB | ~25 MB int8 |
| Licence | varies, often restrictive | `all-MiniLM-L6-v2` Apache-2.0, `bge-small-en-v1.5` MIT |
| Determinism | no | yes |
| **Shippable in this library** | **never** | **yes, as an optional artifact** |

The encoder is bundled — in a separate optional module, with the core degrading to lexical scoring
when it is absent. The generator is always **bring-your-own**, reached through the same offline file
exchange `enrich-targets` / `enrich-apply` already uses. The operator supplies the model; the library
orchestrates, budgets and verifies.

### Three tiers

**Tier 0 — deterministic, free, every node.** Compose the indexed text from the AST itself:
camel-case-split identifiers (already done), package path, supertypes, signature types, **annotation
literals**, and javadoc first sentences. The graph already carries the annotation values —
`annotation.KafkaListener.topics: payment-authorized`, `annotation.Table.name: CUST_ORDER` — and
they are business vocabulary sitting unused. Every token traces to a source range, so Tier 0 breaks
no invariant in the table above.

**Tier 1 — generated, budgeted, pinned.** A one-sentence purpose, written by the operator's model,
only for nodes where Tier 0 comes out uninformative *and* the existing planner ranks them high. Not
500k nodes; a few thousand. `EnrichmentPlanner`, `BranchEnrichment` and the claims gate already
implement the selection, the budget and the confidence cap — what failed before was *what* they were
pointed at (package summaries) and *how the output was consumed* (BM25).

**Tier 2 — encode both, compare siblings.** Brute-force cosine over the ~20 siblings at a frontier.
No ANN index, therefore no further dependency.

### Why the tree is what makes this affordable

This is the argument the design should have made from the start, and did not.

Contextual retrieval as usually practised bakes ancestor context into *every* chunk's vector,
because flat search has no path to inherit from. A descent **inherits context at query time** from
the path it already walked: repository, module and type context ride the frontier instead of being
duplicated into every leaf's embedding.

Combined with node counts — module + package + type is **6,527 of 43,798** nodes on
jackson-databind (15%) and **3,664 of 29,647** on junit5 (12%) — the tree needs roughly one vector
in eight, and no nearest-neighbour structure at all:

| | flat dense | dense over the tree |
| --- | ---: | ---: |
| vectors (jackson-databind) | 43,798 | **6,527** |
| index structure | ANN — another dependency | none |
| shipped index @384d int8 | ~17 MB | **~2.5 MB** |

### The corpus is an overfitting risk, and the profile inverts

The four repositories are framework and infrastructure code. Enterprise business code is the mirror
image, and tuning on one profile will mislead about the other:

| | OSS framework code | enterprise business code |
| --- | --- | --- |
| javadoc | good — public APIs with maintainers | absent, stale, or `/** Gets the value of x. */` |
| identifiers | abstract, domain-free: `TypeBase`, `ContainerNode` | **domain-laden**: `OrderSettlementProcessor` |
| annotations | few, structural | **dense and semantic**, carrying table names, topics, routes |
| string literals | rare | business vocabulary throughout |

So a javadoc-only Tier 0 would likely succeed here and fail on the repositories this library is
meant for. Tier 0 must lean on annotation literals and split identifiers, which survive both
profiles, and the corpus needs a fifth, enterprise-shaped repository before any of this is tuned.

### Risks this introduces

**Index-time cost at enterprise scale.** A generated sentence per node does not survive a 500k-node
repository. Tiering bounds it; the existing snapshot/diff machinery must drive re-enrichment of
changed subtrees only, or every build pays for the whole repository again.

**Unverifiable routing bias — the serious one.** A generated sentence that is subtly wrong does not
produce a wrong *claim*: the chooser contract already prevents that, because a navigation choice
names a place to look and asserts nothing. But it silently biases *routing*, and unlike a claim
there is no citation to check it against. Generated context is therefore **index-only** and must
never be quotable into an answer, on top of the existing ≤0.80 confidence cap.

**Determinism.** Byte-identical output from identical source is a stated invariant, and a generative
model breaks it. Generated context must be a *pinned input artifact* carrying its own fingerprint —
the same shape as the pinned tree — never something recomputed per build.

**And it is unmeasured.** Four interventions have come back negative. This one is a hypothesis with
a mechanism, not a result, and it gets built in the order that can kill it cheapest: Tier 0 first,
on both repository profiles, because it costs nothing and bounds the headroom left for Tier 1.

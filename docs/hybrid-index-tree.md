# A hybrid of the code graph and PageIndex RAG

This is a design plan, not a shipped feature. Nothing described here exists in the codebase yet.

## The idea in one sentence

PageIndex-style RAG replaces "embed chunks, rank by vector similarity" with "build a table of
contents, then let a reasoner walk down it". This document proposes doing that over the code graph
instead of over document text: derive a navigable tree from what the graph already proves, descend
it to choose *where to look*, then use the graph's edges to decide *what to return*.

Retrieval today is the weakest layer in this product. That is the layer this changes. The
verification gate, the provenance rules, and the deterministic model underneath are untouched.

## What PageIndex RAG actually does

Worth stating precisely, because the value of the hybrid depends on which parts transfer.

1. **Index time.** A long document is turned into a hierarchical tree that mirrors its own structure
   — a table of contents. Each tree node carries an id, a title, a short summary, its children, and
   a pointer to the physical region it covers (in PageIndex's case, a page range).
2. **Query time.** The reasoner is shown one node's card — its summary and the ids of its children —
   and picks which children to descend into. It repeats down the levels, keeping a small set of
   candidate branches, until it reaches leaves.
3. **Read.** Only the selected leaves are fetched and read.

Three consequences follow, and all three matter here:

- **No embeddings and no vector store.** Retrieval is a sequence of small reasoning steps over
  structure, not a nearest-neighbour lookup.
- **No fixed-size chunking.** The unit of retrieval is a section the document itself defines, not an
  arbitrary 800-token window.
- **The descent is inspectable.** You can read the path the reasoner took and see where it went
  wrong, which a cosine score cannot give you.

The relevance-by-similarity assumption is what PageIndex drops. "Semantically nearest" and "actually
relevant" diverge badly in code, where `PaymentService`, `PaymentServiceTest`,
`LegacyPaymentService` and a `payment` field on an unrelated DTO all look alike to an embedding and
mean entirely different things to an engineer.

## Why this repository is an unusually good host for it

Three facts about the current code, each of which the hybrid depends on.

**The hierarchy already exists, unmaterialized.** `Modules.detect` derives subsystems from build
layout or package prefix. `Capabilities.detect` groups the operational surface by route root and
topic root. `Workflows` walks every entry point to the tables and topics it touches. Packages,
types, and members are in the graph from the analyzer. That is a five-level table of contents
already, expressed only as `CONTAINS` and `PARTICIPATES_IN` edges — never assembled into something
navigable.

**Retrieval is flat and lands on exactly one anchor.** `Bm25Index.over(graph)` indexes every
non-external node as an independent document with no notion of containment. `QueryPlanner.plan` then
narrows to `Optional<GraphNode> subject` and builds context from that single node. Questions with
inherently plural answers — "which endpoints touch the owners table", "what does the billing module
depend on" — cannot be answered well by construction, and `compress()` encodes the same assumption
by sorting evidence on whether an edge `touches(edge, subjectId)`.

**The roadmap already names the missing measurement.** Milestone 4 records that ranking quality
(precision@k, MRR) "is the next missing metric, and the one that matters for large repos". A tree
navigator is precisely a ranking mechanism, so it cannot honestly be evaluated until that metric
exists.

There is also a fourth alignment worth noting. The roadmap says a vector RAG baseline is still
blocked because it "needs an embedding model that runs locally without credentials". PageIndex-style
retrieval needs no embedding model at all. In its deterministic form it needs no model at all.

## Where the analogy transfers, and where it breaks

| PageIndex over documents | This proposal over the graph |
| --- | --- |
| Tree is generated by an LLM reading the document | Tree is **derived deterministically** from graph structure |
| Node covers a page range | Node covers a **set of graph node ids**, each with file:line provenance |
| Node summary is model-written prose | Summary is deterministic facts, plus an **optional pinned claim** capped at 0.80 |
| Leaves are read as raw text | Leaves are expanded into a `ContextPacket` and **traversed** |
| Document has no cross-references | The graph has edges, so retrieval does not stop at the leaf |

The last two rows are where the hybrid beats both parents. A tree tells you *where* the relevant
region is; it cannot tell you that a change there breaks a controller three hops away. The graph
can. Descent locates, traversal reaches.

The first row is where it beats PageIndex on integrity. PageIndex must trust a model to build the
tree correctly, because a document's structure is only recoverable by reading it. A Java repository
states its structure — build layout, packages, declarations, routes — so the tree can be derived
under the same evidence rules as every other layer here, and re-derived byte-identically.

## The design

```text
CodeGraph (deterministic, schema 0.3)
   │
   ├─ derive ──▶ IndexTree                    index:repo
   │             pinned artifact                 └─ index:module:…
   │             + graph fingerprint                 └─ index:capability:… | index:package:…
   │                                                     └─ index:type:…
   │                                                         └─ leaves → { METHOD, ENDPOINT, TABLE, TOPIC }
   │                                             every node lists the graph ids it stands for
   │
question ──▶ QueryPlanner.classify              unchanged: keyword, fast, inspectable
         ──▶ navigate(tree, question, beam)
         │      ├── DeterministicNavigator      card BM25 × kind prior × query-kind affinity
         │      └── AssistantNavigator          offline file protocol; chooses only presented ids
         ──▶ anchor SET  (not one subject)
         ──▶ GraphQueries.context per anchor → merge → compress to budget
         ──▶ VerifiedAnswer.verify              unchanged gate, unchanged invariants
```

### The node card

This is the PageIndex summary page, translated. It is what a navigator — deterministic or model —
actually sees:

```text
index:capability:owners          kind=BUSINESS_CAPABILITY   graphIds=[capability:owners]
  entryPoints 6   entities 2   types 4   unresolvedEdges 3
  exemplars: OwnerController, OwnerRepository, table:owners, GET:/owners/{ownerId}
  children:  index:endpoint:GET:/owners/{ownerId}
             index:endpoint:POST:/owners/new
             index:type:org.springframework.samples.petclinic.owner.OwnerController
             …
  summary (claim ≤0.80): "Owner registration and lookup"
```

Every line above the summary is derived. The summary line is the one place a model's opinion
appears, and it arrives through machinery that already exists: `EnrichmentClaims.ClaimKind.NAME` and
`SUMMARY`, capped at `MAX_CLAIM_CONFIDENCE`, pinned to a committed claims file, verified before
application. `Capabilities` anticipates exactly this in its own javadoc — naming a capability
"Owner registration" rather than "owners" is the ambiguous, high-value judgement the enrichment
budget exists for.

The corollary is a scheduling insight: **enrich branch nodes, not leaf methods**. One good summary
on a high-fan-out branch steers every descent that passes through it. A summary on a leaf method is
read once.

### Navigation, and why a model here is safe

Beam search over cards, with a node budget. Two interchangeable navigators behind one interface:

- **`DeterministicNavigator`** scores each child card by BM25 over its card text, multiplied by a
  kind prior (reuse the weights already in `Bm25Index.prior`) and a query-kind affinity taken from
  `QueryPlanner.QueryKind` — `ENDPOINT` favours capability and endpoint branches, `PERSISTENCE`
  favours table branches, `STRUCTURE` stops at module level rather than descending to methods. Needs
  no model, no credentials, no network. This is the default.
- **`AssistantNavigator`** hands the same card to an assistant through a file exchange, in the shape
  `docs/enrichment-with-a-chat-assistant.md` already establishes: the tool writes navigation
  packets, the assistant writes back chosen child ids, the tool reads them. **An id that was not in
  the presented set is rejected.** The product still never calls a model.

The safety property is structural rather than procedural: a navigation choice is not a claim. The
model selects from a fixed set of ids it was shown; it never asserts a fact, never names a symbol,
never proposes an edge. So it needs no confidence tier, no dispute path, and no new verification
rule. A bad descent costs recall, which the benchmark measures. It cannot corrupt the model.

Contrast that with what a summary is: an assertion about what code means, which goes through the
existing claims gate precisely because it *can* be wrong in a way that matters.

### Multi-anchor output

Descent naturally yields a set of leaves, not one. That is the point, and it is also the change with
the largest blast radius in the existing code:

- `QueryPlanner.Answerable.subject` becomes an anchor list.
- `compress()` needs per-anchor budget allocation instead of one `subjectId` sort key.
- `VerifiedAnswer.claimsFrom` must anchor each claim to the right subject. It already refuses to
  attribute a one-hop edge to the packet subject — that logic extends to N anchors; it must not be
  loosened to accommodate them.

## Sequencing

Ordered so that each phase is independently useful and the expensive phases are the last ones.

**Phase 0 — measure what you are replacing.** Add `precision@k`, `MRR`, and **anchor recall** (did
the expected subject appear in the anchor set at all) to `EvaluationHarness`, plus a
`--retrieval-only` mode that scores anchor selection separately from packet construction. Record the
flat-BM25 baseline across all four question sets. Do this before the tree exists, or "the tree
helped" is unfalsifiable. Worth doing on its own merits even if the rest is never built.

**Phase 1 — `modules/index-tree`, derivation only.** `IndexTree.derive(CodeGraph)` produces nodes
with `id`, `kind`, `name`, `graphIds`, `children`, and deterministic counters. Axis selection mirrors
`Modules`: multi-source-root repositories branch by module, single-module repositories branch by
package, and the capability axis appears only where endpoints or topics exist. Ship as a pinned
artifact — `repo-intel index <repo> -o tree.json` — carrying a graph fingerprint, and refuse a stale
tree the way `GraphSnapshot.read` refuses a mismatched schema version.

**Phase 2 — deterministic navigator, behind a flag.** `ask --retrieval TREE|BM25|HYBRID`, defaulting
to `BM25`. Run the Phase-0 metrics on all three configurations.

**Phase 3 — multi-anchor packets.** Only after Phase 2 shows the anchors are genuinely better.
Widening packets before that is pure cost.

**Phase 4 — assistant navigator.** Offline packets, chosen-ids-only protocol, and the descent
persisted as an auditable navigation trace.

**Phase 5 — branch summaries.** Retarget `EnrichmentPlanner.rank` at tree branch nodes, scoring by
fan-out and query likelihood rather than incoming degree alone, then re-run Phase 0 to prove the
summaries improve descent. If they do not, that is cheap to discover and worth knowing.

## The configuration to expect to win

Not tree-instead-of-BM25. **The union of both.**

Tree descent produces structurally coherent anchors and fails by committing to a wrong branch early.
Flat BM25 produces incoherent anchors and never has that failure mode, because it never made a
choice. Taking top-*n* from each, deduplicating, and splitting the budget covers the other's
weakness. That is what `HYBRID` should mean, and the benchmark decides whether it becomes the
default.

Early branch commitment is worse on code than on prose, because names repeat across modules in a way
section titles in a document do not. `OwnerController` and `OwnerRestController` in different source
roots are a realistic way to lose a descent at level one.

## Invariants this must not break

| Invariant | How the design holds it |
| --- | --- |
| Same source, same output, any machine | Tree derived by sorted traversal; no `Set.of`/`Map.of` on any ordering path — the hazard `docs/architecture.md` explicitly flags |
| No relation without evidence | Tree nodes point at graph ids; they assert nothing the graph does not already carry |
| A model may describe, not extend | Navigation selects presented ids; summaries go through the existing claims gate at ≤0.80 |
| Deterministic path needs no LLM | `DeterministicNavigator` is the default and is model-free end to end |
| Local-first, no network | Assistant navigation is a file exchange, identical in shape to `enrich-targets` / `enrich-apply` |
| Ids are stable and non-colliding | Tree ids are prefixed `index:` and live in a separate artifact, outside graph schema 0.3 |

## Risks, stated before they are discovered

**Degenerate repository shapes.** jackson-databind has no framework at all: no endpoints, no
capabilities, so the capability axis is empty and the tree must degrade to package and type levels.
Petclinic is single-module, so level one is the package-prefix fallback and may be nearly flat.
junit5's 27 source roots is the favourable case. Test all three; the fixture proves nothing here.

**Fan-out.** A package with 500 types produces a card no reasoner can read and no scorer can
discriminate over. Needs deterministic sub-bucketing — alphabetical, or via `Communities` — with
stable synthetic group nodes and a hard cap on card size.

**Index cost.** The roadmap already lists index cost as a reportable metric. Derivation must not
become a second full graph traversal per query; it is built once per graph and pinned.

**Staleness.** An index tree pinned next to a graph that has moved on is worse than no tree. The
fingerprint check is not optional, and it should fail loudly in the style `GraphSnapshot` already
uses.

**Latency in assistant mode.** Descent costs roughly depth × beam model round trips. Deterministic
mode costs none. Report both.

## What this deliberately does not do

- It does not replace BM25. Flat retrieval stays as a baseline, as an escape hatch, and as half of
  the hybrid.
- It does not put the tree inside graph schema 0.3. Separate artifact first; fold it in only if it
  earns the churn.
- It does not make the assistant navigator the default. It is an option that improves quality where
  a model is available, never a dependency.
- It does not let a model author tree structure. A model may name a branch. It may not invent one.

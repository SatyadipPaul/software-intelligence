# The 200-question corpus, and what it says about retrieval

Date: 2026-09-16. JDK 25, single run, four repositories at the commits their question sets pin:
the fixture, spring-petclinic `88e37c1`, jackson-databind `2b72ff3`, junit5 `de6d621`. Build
classpaths supplied for all three real repositories (see [the classpath run](classpath-2026-09-16.md);
they change no retrieval number, but they are the analyzer's real configuration).

Milestone 4 asked for 200+ grounded questions across 3–5 Java repositories. The corpus now holds
exactly 200: 25 on the fixture, 50 on spring-petclinic, 70 on jackson-databind, 55 on junit5. Every
one was written by reading the source at the pinned commit, never from tool output, and every one is
verified by the traversal harness: 25/25, 50/50, 70/70, 55/55, with structural accuracy, evidence
recall and groundedness all 1.000.

The corpus was grown deliberately lopsided. 161 of the 200 questions never say the name of the
symbol they are about; they describe what the code *does* — "which node stands for an explicit JSON
null", "what aborts a test rather than failing it". 39 name their subject outright, which is the
shape the corpus used to be made of.

## What the corpus is actually measuring

Split the same 200 questions by whether the question says its subject's name:

| Repository | names its subject | does not |
| --- | ---: | ---: |
| sample-commerce | 8/8 = 1.000 | 9/17 = 0.529 |
| spring-petclinic | 12/12 = 1.000 | 14/38 = 0.368 |
| jackson-databind | 10/10 = 1.000 | 5/60 = 0.083 |
| junit5 | 8/9 = 0.889 | 1/46 = 0.022 |
| **all 200** | **38/39 = 0.974** | **29/161 = 0.180** |

That is the finding, and it is larger than any difference between the retrieval modes. Retrieval
here is an exact-name matcher. Say the name and it is found essentially always; describe the thing
instead and it is found 18% of the time — and the rate falls with repository size, from 0.529 on a
ten-class fixture to 0.022 on junit5, where 45 of 46 subject-free questions miss.

Both modes fail the same questions. On junit5, "which annotation switches a test off without
deleting it" does not reach `Disabled` by descent or by ranking, because nothing in `Disabled.java`
or on its card contains the word *switches*, *off*, or *deleting*. The word the asker would use and
the word the author typed are different words, and neither BM25 over identifiers nor a descent over
cards built from identifiers can bridge that.

## The exit criterion is not met

Milestone 6 said: *tree-navigated retrieval beats flat BM25 on recall@k, MRR, and anchor recall
across all four question sets — or is dropped, having been measured rather than assumed.*

On 200 questions it does not beat flat retrieval across all four sets:

- **spring-petclinic**: TREE wins on every metric (MRR 0.441 against 0.369, anchor coverage 0.246
  against 0.031). Unambiguous.
- **sample-commerce**: TREE wins rank and coverage (MRR 0.553 against 0.531, coverage 0.321 against
  0.143) and loses anchor recall (0.680 against 0.720). Split.
- **jackson-databind** and **junit5**: indistinguishable. Every gap is one question — BM25 reaches
  10 subjects on junit5 where TREE reaches 9; on jackson both reach 15. At those magnitudes the
  ordering is noise, not a result.

The earlier claim that **HYBRID is never worse than flat retrieval** was true of the 53-question
corpus and is not true of this one. It was an artifact of a corpus in which most questions named
their subject, where both modes score 1.000 and nothing can separate them. Recording it as met was
premature; it is withdrawn here rather than defended.

**What survives.** Two things, both still worth having:

1. **Anchor coverage**, the only metric that scores a *set* rather than one symbol, is where the
   descent is clearly ahead wherever it is non-zero: 0.246 against 0.031 on Petclinic, 0.321 against
   0.143 on the fixture. A descent lands on containers; flat ranking lands on individual symbols
   that happen to score well.
2. **Cost.** At scale the descent stays cheaper — 53 ms against 59 on jackson-databind, 38 against
   47 on junit5 — because it reads about 20 cards where flat ranking scores 45,595 nodes.

So `HYBRID` stays the default: it is the cheaper path, it is ahead on coverage, and the two
corpora where it trails do so by one question. But it is no longer described as beating flat
retrieval, because on this corpus it does not.

## What would actually move the number

Every measurement in this repository so far has come back negative — branch summaries, the blind
re-run of them, build classpaths, and now the tree itself at scale. They have one thing in common:
each enriches the *structure* around identifiers while leaving the identifiers themselves as the
only vocabulary retrieval can match. The split table above says the bottleneck is the vocabulary
gap, and nothing tried so far touches it.

The two candidates that would are an embedding model over card text, which the local-first
invariant has deferred for want of one that runs without credentials, and query expansion from the
code's own prose — javadoc, not package summaries. The blind summary experiment showed
maintainer-written package prose does not carry the asker's words; whether *method-level* javadoc
does is a different question and an unmeasured one.

## Reproduce

```bash
repo-intel evaluate <repo> evaluation/<repo>.questions.tsv --fail-under 0 --discover-classpath
repo-intel evaluate <repo> evaluation/<repo>.questions.tsv \
  --retrieval-only BM25,TREE,HYBRID --fail-under 0 --discover-classpath
```
